the one claim

An unfiltered query is still a safe query.

This is the query that gets written when you are moving fast, and there is one in almost every codebase. It asks for every invoice in the table and it never mentions who is asking. Watch what three different people get back from it.

the app’s actual queryunchanged

select id, customer, amount
from invoices
-- no where clause. no tenant id. nothing.

Nothing above was rewritten, proxied or inspected. The rows are decided by row-level security policies on the table itself, under a role that cannot bypass them and does not own them. An app with a bug, a careless ORM call, a leaked API route and an AI agent all hit the same wall, because it is not in the app.

what happens when you push

Five steps, and any one of them can say no.

Detect

Reads the repository and names the stack: the framework, the database library, where the migrations live, how they are run. Deterministic. If it cannot tell, it says so instead of guessing.

Ask

The few things a schema cannot tell anyone — who your users are to each other, what is shared, what is private, what is sensitive. In English, once. No answer, no launch.

Derive

Your answers and your tables become an access model, built from five policy templates and nothing else. Every policy covers select, insert, update and delete, with both using and with check. You read it back in plain sentences and confirm it before anything is written.

Attack

Your migrations run in a throwaway database inside a container, and the result is attacked there: every table, every verb, every persona, as the app’s own role and again as an agent’s. The expectations come from the seeding plan, never from reading the policies back — so a wrong policy cannot grade its own paper.

Cut over

The new version starts beside the old one and gets no traffic until it passes the health gate several times in a row. Then the proxy moves, requests in flight are allowed to finish, and only then is the old one stopped. A version that never gets healthy never gets a single request.

what a run covers

Every claim here is a re-runnable test.

4verbs probed on every table
5policy templates, and no other sql
2roles attacked, results compared
0failures tolerated

The suite runs once as the role your app connects with and once as the role an AI agent connects with. Both answers are kept. If they differ by one row, the agent can exceed the person it works for, and the deploy stops. The access model and its results are saved on every run — including the runs that failed.

and when something goes wrong anyway

Interrupted is not the same as broken.

Nothing runs twice

Work is claimed with a renewed lease and a fencing token. A worker that stalls loses its claim; if it wakes up later, its writes are rejected rather than applied on top of somebody else’s.

A stale worker cannot route traffic

Traffic is only ever granted by a write that the fence protects, and every container we start is labelled with the app, the generation and the deployment that owns it. Leftovers are reaped, not inherited.

It picks up where it stopped

Kill the machine mid-deploy and a reconciliation loop works out what actually exists, adopts what is ours, re-states the route table from the database and either resumes the deploy or blocks it with a reason.

Your code never runs as us

Your migrations are code we have never read, so they run in a container, never as a subprocess of the worker — and the database they are proved against is a throwaway instance no app lives in.

the part nobody prints

What this proves, and what it does not.

A report that does not carry its own limits is marketing. Here are both halves, in the same type.

covered

  • the schema hash and access model version
  • all four database roles, by name
  • select, insert, update and delete
  • owner, second user, admin, anonymous
  • app role and agent role, compared
  • every policy template actually in use

not covered

  • application logic above the database
  • side channels and timing
  • the migrator role and the platform operator
  • network isolation between your apps
  • denial of service
  • any database reached outside the proven schema

Container isolation here is defence in depth, not a sandbox. Anyone who can deploy to an installation can run code on it, which is why an installation belongs to one team.
